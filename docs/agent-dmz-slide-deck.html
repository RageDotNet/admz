The LLM DMZ
A Directory-Driven Broker Between Untrusted AI Agents
System Design v2
rage.net  ·  Architecture & Product Review  ·  2026
1

The Problem

Direct agent-to-agent

  • Client prompts are an injection surface
  • Provider responses can exfiltrate data
  • No neutral contract between parties
  • No audit trail of what crossed

Through the DMZ

  • Every payload validated against a JSON Schema
  • LLM arbiter judges intent on both sides
  • Human approval happens before traffic
  • Full request log for after-the-fact review

One side's prompt is the other side's attack surface. The DMZ is the neutral ground between them.

2

What the DMZ Is

📡

Directory

Catalog of registered actions — filterable per client by access state

🛂

Broker

Validates, arbitrates, dispatches, retries — every message crosses guarded

📋

Log

Every request, decision, and state change persisted for review

  • Action — a named capability: request schema + response schema + arbiter/model-facing instructions
  • Agent — any registered participant (client, provider, or both); every agent has a bearer key
  • Enrollment — client permission to invoke a specific action, approved by an admin
3

Governance: Approval Upstream, Automation Live

Gate 1

Register provider

Admin registers the agent and sets its delivery configuration

Gate 2

Approve action

Admin reviews and approves the schema package — every version

Gate 3

Approve enrollment

Admin approves each client's access to each action

Providers are semi-trusted

Outputs treated as untrusted — validated and arbitrated. The trust boundary is who becomes a provider, not what their process can do.

No human in the live loop

No code path leaves a client waiting on human action. Rejections are immediate and final; the client's model self-corrects on its next attempt.

4

Agents & Capability Flags

Identity

  • Admin registers agents via webui; bearer key generated and shown exactly once
  • Key revocation cuts the agent off immediately
  • Agents live in the database, never in config files

Roles = independent flags

  • is_client and is_provider — not a role enum
  • "Both" is just both flags true — no special-case code
  • Revoke one capability without touching the other
  • New capabilities become new flags

Endpoint-per-provider

One delivery configuration per provider — all of its actions are served through it. Not endpoint-per-action.

5

Action Lifecycle & Versioning

1 Provider submits schema package via POST /v2/actions → version submitted
2 Automated checks: duplicate id, schema compilation — fail fast with 4xx
3 Admin reviews full submission in webui → approve or reject
4 Approve → version active atomically; prior version becomes superseded

Edit = new version

Old version keeps serving until the new one is approved. Zero-downtime swaps, atomic cut-over. Versioning is PUT.

Withdraw = soft delete

Immediately non-invokable and hidden from discovery; history, versions, logs, and enrollments retained for audit.

6

The Schema Package

One JSON document = one action version

FieldRequiredWho it's for
id + description✅Discovery — clients find the action
request_schema / response_schema✅The wire contract (draft 2020-12)
request/response_arbiter_instructions❌Arbiter — tune what gets flagged
client_instructions❌Client's model — how to build the request
provider_instructions❌Provider's model — how to build the response
request_risk / response_risk❌Scope the arbiter: injection or exfiltration

No provider field

Ownership is derived from authentication — providers can't claim each other's actions.

Instructions are attack surface

Every instruction block is human-reviewed before an action goes live.

7

Two Validation Layers

Layer 1

Structural

  • JSON Schema (draft 2020-12) validation
  • Second pass: Pydantic model via dydantic
  • additionalProperties: false — nothing undeclared crosses
Layer 2

LLM Arbiter

  • Requests → injection, jailbreak, schema-bypass
  • Responses → exfiltration, bulk dumps, leakage
  • Per-action instructions appended to base prompts

Risk scoping fixes arbiter over-rejection: judge security, not data quality. "Could be interpreted as an instruction" is not an attack — it's data.

  • request_risk: injection — only imperative instructions to a model count; everything else is data
  • response_risk: exfiltration — only content beyond the contract counts; verbose ≠ malicious
  • Verdict: {"approved": bool, "reason": "..."} — unparseable verdict = failed check
8

The Lethal Trifecta — and Where the DMZ Cuts It

🔑

Private data

Response schema + exfiltration arbiter gate every outbound payload. No undeclared field crosses.

📥

Untrusted content

Request schema + injection arbiter screen every inbound payload before it reaches a provider.

⚡

External actions

Human-approved enrollment per action. Blast radius scoped, instantly revocable, fully logged.

The DMZ doesn't remove the three legs — it inserts a validated, arbitrated choke point on every wire between them. Injection never gets a straight path.

9

The Request Flow — One Round Trip

1 Authenticate (bearer key → agent + flags)
2 Authorize (enrolled on this action?)
3 Validate request: schema → arbiter · fail = immediate rejection
4 Dispatch to provider endpoint
5 Validate response · fail = retry ×2, then 502

6 · Deliver

Validated response returned immediately — result, action id, and active version number.

7 · Log

Payloads, outcomes, retries, verdicts — persisted for admin review. Observational only.

Transparent failures

Rejections carry the verbatim reason — schema errors or arbiter verdict — so the client's model self-corrects next attempt.

10

Dispatch: Three Provider Protocols

post

HTTP endpoint

Plain POST with passthrough headers. 2xx body must parse + validate.

exec

Local program

Pipe payload to stdin, read stdout. No sandbox in v1 — trust the provider, validate the output.

completions

LLM endpoint

OpenAI-compatible. System = instructions + schema; user = request JSON.

Retry with feedback

Every failure class is retryable, and the retry carries the previous error to the provider so it can self-correct — the same courtesy the DMZ extends to clients.

Bounded worst case

180s timeout × (2 retries + 1) ≈ 9 min max. A hung provider can never hold a connection indefinitely.

10

Security Posture

What's guaranteed

  • Provider outputs can't bypass validation — no response content escapes the pipeline
  • Delivery configs never returned to agents via API
  • Every request, decision, and state change persisted
  • Worst-case duration is finite and configured

The deliberate trade-off

  • exec = arbitrary local code on the DMZ host. No sandbox in v2.
  • Accepted because 3 human gates precede any exec dispatch
  • Explicit non-claim: no isolation from a malicious trusted provider
  • Containerization = future hardening item

The trust boundary is who becomes a provider — not what their process can do.

Client directory view

available requested rejected enrolled

A projection of enrollment + action state — not separate entities.

Failure taxonomy

  • 4xx — your fault; reason returned verbatim, fix and retry
  • 502 provider_failed — provider's fault after retries
  • 503 arbiter_unavailable — no dispatch happened; safe to retry
12

Bootstrap: GET /v2/skill

Client skill

  • Authenticate, browse, interpret enrollment states
  • Request enrollment, invoke actions
  • What rejections and provider-failures mean

Provider skill

  • Register and version actions
  • Submit schemas + instruction fields
  • Interpret approval states; dispatch guarantees

Bearer key + one GET = complete onboarding. The skill document is the integration contract — no docs site, no SDK.

14

Admin Console — Where Humans Decide

Directory

All actions & versions, inline approve/reject, per-action detail: definition, versions + diffs, access, invocations — one screen.

Enrollments

Cross-action queue; approve/reject in ≤ 2 clicks. Same store as per-action view — two views, one state.

Agents

Register, toggle flags, configure delivery, revoke/reissue keys — reveal-once, never retrievable.

Request log

Every call: payloads, verdicts, retries, deciding stage. Observational — no manual actions.

Audit trail

Every state change, append-only, filterable, linked to objects.

Zero JS, zero build

Datastar + Bootstrap 5. No npm, no Node, no bundler.

Every mutating console endpoint also takes the admin bearer token — the whole decision surface is scriptable.

Canonical State Models

Version

submitted → active ⇄ superseded
submitted → rejected (terminal)

Exactly one active per action — always.

Action

pending → active → withdrawn

Withdrawn = soft delete; history retained.

Enrollment

requested → enrolled / rejected
enrolled → revoked

Revocation takes effect immediately.

These tokens are authoritative — every API response, document, and UI badge speaks exactly this vocabulary. Client directory views are projections of it.

16

Non-Goals & NFRs

Out for v2

  • A2A / MCP front doors — REST only
  • Async conventions — provider's own problem
  • exec sandboxing — future hardening
  • Streaming, webhooks, rate limits

Must hold

  • Test suite fully offline (mocked LLM/providers)
  • Bad config crashes loudly at boot
  • No SQL dialect leaks — DB swap = config change
  • Everything auditable, nothing waits on a human
